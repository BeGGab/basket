# Методология покрытия автоматизированными тестами

## 1. Назначение

Документ определяет требования к полноте автоматизированного тестирования пользовательского интерфейса GreenMarket.

Его задача — обеспечить проверку не отдельных пользовательских сценариев, а соответствия всей системы:

* техническому заданию;
* REST API;
* FSM Platform;
* пользовательскому интерфейсу.

Документ обязателен для всех Playwright-сценариев проекта.

---

# 2. Основной принцип

Полнота тестирования определяется не количеством тестов, а полнотой покрытия системы.

Для любого требования проекта должен существовать ответ на вопрос:

> Каким автоматическим тестом оно проверяется?

Отсутствие такого ответа считается дефектом тестового покрытия.

---

# 3. Единицы покрытия

Тестирование выполняется одновременно на нескольких уровнях.

## 3.1 Пользовательские сценарии

Проверяются все основные пользовательские действия.

Примеры:

* просмотр каталога;
* открытие карточки товара;
* поиск;
* фильтрация;
* выбор продавца;
* просмотр фотографий;
* добавление товара в корзину;
* изменение количества;
* оформление заказа.

---

## 3.2 Экраны

Для каждого экрана проверяются:

* открытие;
* получение данных;
* отображение данных;
* обновление;
* закрытие;
* возврат назад.

---

## 3.3 Состояния экранов

Для каждого экрана должны существовать проверки:

* Loading
* Success
* Empty
* Error
* Refresh

---

## 3.4 REST API

Каждый endpoint должен иметь автоматические проверки соответствия интерфейсу.

Для каждого поля контракта определяется одно из состояний:

* отображается пользователю;
* используется внутренней логикой;
* зарезервировано;
* не используется.

Если поле отображается пользователю, Playwright обязан проверить корректность его отображения.

---

## 3.5 Модели данных

Каждое поле модели должно иметь покрытие.

Например

Product

* id
* name
* description
* category
* offers

Offer

* sellerId
* sellerName
* price
* currency
* photos
* availability

Наличие поля в контракте без проверки считается неполным покрытием.

---

## 3.6 Коллекции

Каждый массив проверяется минимум в трех вариантах.

* пустой массив
* один элемент
* несколько элементов

Например

offers.photos

обязательно проверяются случаи

* 0 фотографий
* 1 фотография
* 3 фотографии

Тест обязан проверить соответствие количества отображаемых элементов данным REST API.

---

## 3.7 Nullable-поля

Каждое nullable-поле проверяется в двух состояниях.

* значение присутствует
* значение отсутствует

---

## 3.8 Пользовательские действия

Каждый интерактивный элемент обязан иметь тест.

Примеры

* кнопки
* ссылки
* карточки
* фильтры
* сортировки
* поиск
* меню
* переключатели

---

## 3.9 Навигация

Проверяются все маршруты пользователя.

Например

Каталог

↓

Карточка товара

↓

Карточка продавца

↓

Корзина

↓

Оформление заказа

---

## 3.10 FSM

Если экран работает через FSM Platform, проверяются

* все состояния;
* все разрешенные переходы;
* невозможность запрещенных переходов;
* корректность отображения каждого состояния.

---

# 4. Матрица покрытия

Для каждого экрана должна существовать матрица покрытия.

| Проверка                  | Статус |
| ------------------------- | ------ |
| Пользовательские действия |        |
| REST API                  |        |
| Поля модели               |        |
| Nullable                  |        |
| Коллекции                 |        |
| Ошибки API                |        |
| Состояния экрана          |        |
| Навигация                 |        |
| FSM                       |        |

---

# 5. Traceability

Каждое требование должно прослеживаться по цепочке

Техническое задание

↓

REST API

↓

Экран

↓

Playwright-сценарий

↓

Playwright Report

Для любого требования должна существовать возможность быстро определить автоматический тест, который его проверяет.

---

# 6. Критерии полноты

Тестовое покрытие считается достаточным только при выполнении всех условий.

### Пользовательские сценарии

Проверены все пользовательские действия.

### REST API

Проверены все endpoint.

### Контракты

Каждое поле контракта либо отображается, либо явно отмечено как неиспользуемое.

### Модели

Проверены все поля моделей.

### Коллекции

Каждый массив проверен для случаев

* 0 элементов
* 1 элемент
* N элементов

### Nullable

Проверены оба варианта.

### Ошибки

Проверены все варианты ошибок API.

### Навигация

Проверены все основные маршруты пользователя.

### FSM

Проверены все состояния и все переходы.

---

# 7. Правила разработки

Любая новая функциональность считается завершенной только после выполнения следующих условий.

* обновлено техническое задание;
* обновлен REST API (при необходимости);
* реализован пользовательский интерфейс;
* написаны Playwright-сценарии;
* обновлена матрица покрытия;
* все тесты проходят успешно.

---

# 8. Типовые причины неполного покрытия

Наличие тестов не означает полноту покрытия.

Примеры недостаточного покрытия:

* проверяется только успешный сценарий;
* проверяется только наличие элемента, но не его содержимое;
* проверяется только первый элемент массива;
* отсутствуют проверки пустых коллекций;
* отсутствуют проверки nullable-полей;
* отсутствуют проверки ошибок API;
* отсутствует проверка соответствия UI контракту REST API.

---

# 9. Пример обнаруженного пробела

При тестировании карточки товара было выявлено следующее.

REST API возвращал массив `offers[].photos`, содержащий три фотографии.

Пользовательский интерфейс отображал только первую фотографию массива.

Playwright-сценарии проверяли лишь наличие изображения на странице и поэтому успешно проходили.

Причина — отсутствие обязательной проверки соответствия количества отображаемых фотографий данным REST API.

После обнаружения данного случая в методологию добавлено правило:

> Для любого массива, влияющего на пользовательский интерфейс, автоматические тесты обязаны проверять отображение случаев 0, 1 и N элементов, а также соответствие количества отображаемых элементов данным, полученным от REST API.

---

# 10. Цель документа

Настоящий документ используется как критерий приемки автоматизированного тестирования.

Добавление новых функций или изменение существующих считается завершенным только после достижения полного покрытия в соответствии с настоящей методологией.
