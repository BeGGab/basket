# AI-first Development Process MVP v1.0

## Статус

**Версия:** 1.0 (MVP)

## Назначение

Определить минимальный процесс AI-first разработки, который команда может начать использовать немедленно.

Документ сознательно ограничен только теми практиками, которые имеют низкую стоимость внедрения и могут быть проверены на реальных задачах.

Это не описание идеальной методологии.

# Основные принципы

## Принцип 1. MVP прежде методологии

Методология развивается так же, как продукт.

Сначала создаётся минимально полезный процесс.

Только после получения практического опыта принимаются решения о его развитии.

## Принцип 2. AI-first

ИИ используется первым инженерным помощником.

Он помогает анализировать требования, проектировать решение, писать код, тесты и документацию.

Окончательные инженерные решения принимает разработчик.

## Принцип 3. Простота

Любое усложнение процесса допускается только после появления подтверждённой практикой проблемы.

Гипотетические риски не являются основанием для добавления новых правил.

## Принцип 4. Анализ прежде реализации

Сложная задача сначала анализируется и декомпозируется.

Реализация начинается только после того, как стало понятно, что именно необходимо сделать.

# Роли

## Ответственный за процесс

В каждой команде назначается ответственный за соблюдение процесса. Обычно это Tech Lead или один из разработчиков.

Он:

- проводит ретроспективы;
- следит за соблюдением Правила 0;
- фиксирует решения ретроспектив;
- не изменяет процесс между ретроспективами, кроме случаев, предусмотренных Правилом 0.

# Процесс выполнения задачи

## Шаг 1. Классификация задачи

Перед началом работы разработчик самостоятельно определяет уровень задачи.

**L0**

Небольшие изменения:

- локализация;
- простые багфиксы;
- CSS;
- небольшие правки UI.

**L1**

Обычная разработка:

- новая функциональность;
- новый экран;
- новый компонент;
- изменение существующего поведения.

**L2**

Архитектурные изменения:

- изменение платформенных компонентов;
- изменение архитектуры;
- изменение контрактов;
- изменение фундаментальных решений.

Классификация выполняется разработчиком.

Если в процессе работы выяснилось, что задача была классифицирована неверно:

- задача не откатывается назад;
- выполняется до завершения по текущему сценарию;
- помечается как **Misclassified**;
- случай рассматривается на ближайшей ретроспективе.

Ошибочная классификация считается нормальной частью развития процесса.

## Шаг 2. Context Report

Перед реализацией разработчик использует ИИ для анализа контекста.

Минимальный Context Report отвечает на пять вопросов:

1. Что необходимо сделать?
2. Что уже существует в проекте?
3. Какие документы относятся к задаче?
4. Какие риски уже видны?
5. Какие вопросы пока остаются открытыми?

Для небольших задач L0 допускается краткий Context Report.

Например, несколько строк вместо подробного анализа.

Перед составлением Context Report рекомендуется просмотреть существующие Knowledge Delta по затрагиваемой области проекта.

Если по результатам Context Report выявлено отсутствие утверждённого backlog проекта для задачи уровня L1 либо задача относится к уровню L2, следующим этапом становится Task Decomposition Report. Для задач L0 этап пропускается.

## Шаг 3. Task Decomposition Report

Цель этапа — превратить большую, плохо оцениваемую задачу в набор небольших, независимых и проверяемых задач.

Примеры задач, для которых обычно требуется декомпозиция:

- доработать экран;
- реализовать новую подсистему;
- интегрировать Platform Interface;
- переработать FSM;
- реализовать авторизацию;
- выполнить миграцию архитектуры.

### Анализ выполняется на основании

- требований;
- существующей документации;
- исходного кода;
- архитектуры проекта;
- существующего поведения системы.

Недостаточно анализировать только ТЗ или только пользовательский интерфейс.

При необходимости ИИ должен изучить и существующий код реализации.

### Результатом является Task Decomposition Report

Отчёт должен содержать минимум следующие разделы:

- Что уже реализовано.
- Что реализовано частично.
- Что отсутствует.
- Какие обнаружены дефекты.
- Какие ограничения накладывает текущий Stage проекта.
- Какие новые задачи обнаружены во время анализа.
- Итоговый backlog.

Если в ходе анализа обнаружено, что часть предполагаемых задач уже реализована, они не включаются в backlog повторно.

Каждая задача backlog должна содержать:

- идентификатор;
- краткое описание;
- приоритет;
- при необходимости — зависимость от других задач.

### После завершения Task Decomposition Report

Для команды из одного разработчика утверждение backlog выполняется самим разработчиком.

После утверждения backlog этап декомпозиции считается завершённым.

Дальнейшая работа ведётся исключительно по отдельным задачам backlog.

Например: MAP-001, MAP-002, MAP-003 и так далее.

Каждый Pull Request должен реализовывать одну или несколько логически связанных задач backlog.

### Схема процесса, когда требуется декомпозиция

Было: Классификация → Context Report → Реализация.

Стало: Классификация → Context Report → Task Decomposition Report (для L2, а также для L1 без утверждённого backlog проекта) → Утверждение backlog → ТЗ на отдельный task → Реализация.

## Шаг 4. Реализация

Разработчик выполняет задачу совместно с ИИ.

ИИ может использоваться для:

- анализа требований;
- проектирования;
- написания кода;
- рефакторинга;
- подготовки тестов;
- подготовки документации.

## Шаг 5. Self Review

После завершения реализации ИИ получает собственный результат с инструкцией критически проверить решение.

Цель проверки:

- найти ошибки;
- найти пропущенные сценарии;
- найти возможные регрессии;
- предложить улучшения.

## Шаг 6. Human Review

После самопроверки разработчик самостоятельно проверяет результат.

Процесс AI-first не заменяет инженерное решение человека.

## Шаг 7. Knowledge Delta

После завершения задачи создаётся отдельный документ.

Структура каталога:

```
knowledge-delta/
    MAP-017.md
    CAT-024.md
    UI-003.md
```

Каждый документ отвечает минимум на три вопроса.

### Что нового узнала команда?

### Что следует добавить или изменить в документации?

### Что стоит использовать в следующих задачах?

Для небольших задач L0 допускается краткая запись.

## Шаг 8. Prompt Library

Если разработчик считает использованный промпт полезным, он сохраняет его.

Структура каталога:

```
prompts/
    image_review.md
    playwright_review.md
    map_review.md
```

На этапе MVP:

- критерии качества отсутствуют;
- ревью отсутствует;
- версии отсутствуют.

Допускаются:

- дубли;
- противоречия;
- устаревшие варианты.

Это считается нормальным этапом накопления опыта и не требует предварительной очистки.

# Правила процесса

## Правило 0. Заморозка процесса

Между двумя ретроспективами процесс считается замороженным.

Допускаются только изменения, без которых выполнение процесса становится невозможным либо приводит к существенным потерям времени для всей команды.

Каждое исключение фиксируется сразу после внесения.

Фиксируются:

- дата;
- автор;
- причина;
- изменённое правило;
- краткое обоснование.

Все исключения рассматриваются отдельно на ближайшей ретроспективе.

Если между двумя ретроспективами накопилось большое количество подобных изменений, это считается дефектом процесса, а не нормальной практикой.

## Правило 1. Экономика процесса

До первой ретроспективы все шаги процесса выполняются полностью.

Полезность отдельных шагов во время выполнения задач не обсуждается.

Экономическая эффективность оценивается только на ретроспективе.

По её результатам каждый шаг может быть:

- сохранён;
- упрощён;
- изменён;
- удалён.

## Правило 2. Не проектировать заранее

Запрещается заранее создавать решения для проблем, которые ещё не возникли.

Любое новое правило процесса должно устранять наблюдаемую проблему, а не гипотетический риск.

## Правило 3. Dogfooding

Любое изменение процесса должно пройти минимум десять реальных задач до включения в следующую версию процесса.

Сначала практика.

Потом документ.

Правило не распространяется на изменения, оформленные как исключение Правила 0.

## Правило 4. Удаление правил

На каждой ретроспективе команда обязательно отвечает на два вопроса.

### Что следует добавить?

### Что следует удалить?

Если правило:

- не используется;
- не приносит пользы;
- усложняет работу;
- не окупается,

оно должно быть удалено либо упрощено.

## Правило 5. Сначала декомпозиция

Пока Task Decomposition Report не завершён (в случаях, предусмотренных Шагом 3), реализация не начинается.

Для уже существующих атомарных задач backlog данный этап пропускается.

# Журнал исключений Правила 0

Сюда заносится каждое исключение из Правила 0 сразу после внесения — до его рассмотрения на ближайшей ретроспективе.

## Исключение 1

- **Дата:** 2026-08-08
- **Автор:** _[указать автора]_
- **Причина:** при декомпозиции экрана Map задача была сразу переведена в ТЗ без промежуточного анализа документации и кода, что привело к ошибочному backlog и потребовало полной переделки. Между Context Report и ТЗ отсутствовал обязательный этап, вскрывающий такие расхождения.
- **Изменённое правило:** добавлены Шаг 3 «Task Decomposition Report» и Правило 5 «Сначала декомпозиция».
- **Краткое обоснование:** это исправление обнаруженного на практике дефекта процесса, а не гипотетического риска (не противоречит Правилу 2), поэтому вносится как исключение Правила 0 без ожидания первой ретроспективы. Подлежит рассмотрению на ближайшей ретроспективе наравне с прочими исключениями (см. повестку «Первой ретроспективы»).

# Первая ретроспектива

Проводится через четыре недели после начала использования процесса.

Продолжительность: не более 30 минут.

Ретроспективу проводит ответственный за процесс.

Все решения фиксируются в каталоге:

```
process-retrospectives/
    2026-09-05.md
```

Повестка ретроспективы фиксирована.

1. Что реально помогло?
2. Что никто не использовал?
3. Что раздражало?
4. Что следует удалить?
5. Что стоит автоматизировать?
6. Какие задачи были ошибочно классифицированы?
7. Какие исключения из Правила 0 возникли и почему?

# Что запрещено до первой ретроспективы

До получения практического опыта запрещается внедрять:

- Knowledge Graph;
- Trust Score;
- Benchmark промптов;
- RFC процесса;
- автоматическую эволюцию процесса;
- сложные системы метрик;
- инфраструктуру, которая ещё ни разу не понадобилась в работе.

# Definition of Done

Задача считается завершённой, если:

- выполнена реализация;
- если задача требовала создания или изменения тестов, соответствующие тесты выполнены;
- выполнена Self Review;
- выполнена Human Review;
- создан Knowledge Delta;
- при необходимости сохранён полезный промпт;
- выполнены все задачи backlog, запланированные для данного Pull Request.

# Главный принцип

**Любое новое правило процесса должно устранять наблюдаемую боль, а не гипотетический риск.**

Процесс развивается исключительно на основании практического опыта команды.

Любая идея сначала должна доказать свою полезность в реальной работе, и только после этого стать частью следующей версии процесса.
